# Anthropic — The AI-Native SDLC Playbook

> Notes by Jinto Jose on a public source. Summarised for study; framework, figures and wording belong to the publisher. Part of [ai-native-sdlc-playbooks](../README.md).


**Source:** Anthropic blog, "The AI-Native SDLC playbook," 21 August 2026. Author: Louis Claxton. Derived from Anthropic's Applied AI team practices, informed by customer work.
**Document type:** Vendor playbook.
**Organising principle:** *Every stage commits an artifact the next stage reads.*

## Core thesis

The traditional SDLC is process-heavy, designed to ensure accountability and control at each step, with controls that assume every step is performed by a human. Agentic coding compressed the Build stage; the process around it did not move. To realise the productivity gains of agentic AI *and* secure it, the rest of the lifecycle requires the same degree of transformation that the implementation phase has already undergone.

The AI-native SDLC is described as a reimagined process that **combines the old control objectives with new enforcement**. It promotes automated handover and triggering of subsequent plays, addressing the manual and clunky nature of handoffs between traditional phases.

**Shape of the change.** From a line to a loop. Instead of a linear handoff, the process becomes a loop with Claude embedded at every point, operating in hours rather than weeks, with humans positioned *above* the loop — instigating, directing, and governing.

## Structural facts

- Six stages: **Plan, Design, Build, Test, Deploy, Maintain**
- The stages are explicitly described as **non-linear**
- The plays are the core of the playbook and are **modular** — organisations prioritise different stages based on their needs
- `intent.md` kicks off the process and can enter through different routes
- A dependency graph exists in the source showing which plays require which others

## The security-team framing (the key argument for regulated organisations)

Security teams are sized for human output. When agents multiply code output, one of two things happens: the review queue builds, or code ships under-reviewed. Neither is acceptable in a regulated organisation. Security and policy checks must keep pace with the agents.

## Traditional vs AI-native, by stage

| Stage | Traditional SDLC | AI-native SDLC |
|---|---|---|
| **Plan** | Requirements gathered by committee, written up by hand | Claude synthesises pain points into `intent.md` — human-readable, machine-actionable |
| **Design** | Spec written by analysts, parsed by designers | Requirements + design compressed into one guided session, versioned in git |
| **Build** | Tests and code handwritten; docs written after the fact | Tests and code generated by AI; knowledge lives in `CLAUDE.md` and skills |
| **Test** | QA gates at stage boundaries | Continuous evals woven through implementation |
| **Deploy** | Humans review every line; inconsistent governance | Layered agentic review; human review for regulated/critical code; hooks as gates |
| **Maintain** | Humans watch production for bugs | Agents monitor deployments; breaches write a new `intent.md` |

## The committed artifact chain

This is Anthropic's distinctive contribution. Each stage ends by committing a file the next stage reads. Together these form the audit trail.

| Stage | Artifact | Contents |
|---|---|---|
| Plan | `intent.md` | Problem, outcome, constraints — in the originator's own words |
| Design | `spec.md` | Requirements + design, constrained by org skills |
| Build | `plan.md` | Files, order of work, tests — approved **before** code is written |
| Build | the diff + its tests | Generated code, verified by the session's own feedback loop |
| Test | `evals/` | Real tasks + pass criteria, re-run on every config change |
| Deploy | PR + review findings | Review passes, severities, human approval |
| Maintain | the incident record | Diagnosis is written back as the next `intent.md` |

**Note:** Build commits twice — the approved plan before any code, then the diff and its tests. The chain of commits is the audit trail: who asked for what, what the agent produced, and who approved it.

## Stage detail

### Stage 1 — Plan: capture intent, not tickets

Ideas stop waiting for someone to write them up. Intent is captured once, in the originator's own words, as a version-controlled artifact.

**How it works**
1. Originator describes the problem to Claude, in plain language
2. Claude asks the questions an analyst would: scope, users, constraints, success criteria
3. Claude drafts `intent.md` from the organisation's template
4. Originator corrects any misunderstanding
5. Product owner reviews and commits `intent.md`

**Example `intent.md` structure**
```markdown
# Intent: claims status self-service
Author: J. Ortiz (claims ops) · Status: draft

## Problem
Handlers spend ~1/3 of call time on status-only queries.

## Proposed outcome
Customers see status, next step, and date in the portal.

## Constraints
No new PII in the portal session.

## Open questions
Do loss adjusters need access too?
```

**Measure:** Time from first conversation to a committed `intent.md` — expect a fall from a multi-week refinement cycle to hours.

### Stage 2 — Design: requirements and design in one session

Policy is applied while the spec is written — not discovered in a review weeks later.

**Traditional:** Requirements and design run as separate phases by separate teams. Analysts formalise the idea; designers parse it back into a design. Slow and lossy.

**AI-native:** Both phases happen in one prompted session. Claude takes `intent.md` and produces `spec.md`, constrained by the organisation's brand, security, compliance and UX skills — with concerns flagged.

**Process**
1. Product owner opens session with org skills loaded
2. Attach `intent.md`, name constraints, demand flags
3. Review spec vs. original idea; resolve flagged concerns
4. Commit `spec.md` — which triggers plan mode

### Stage 3 — Build: nothing ships without an accepted plan

Institutional knowledge becomes files the agent reads; guardrails run as code, not habits.

| Play | Description |
|---|---|
| **Plan mode as default** | Claude interviews the engineer from `spec.md`; approved plan is committed as `plan.md` before any file changes |
| **CLAUDE.md** | Commands, conventions, architecture and known mistakes — read at the start of every session, version-controlled |
| **Skills as institutional knowledge** | Explicit, version-controlled policy (security, brand, API standards) applied consistently across sessions |
| **Hooks as guardrails** | Block edits to protected paths, run linters, keep credentials out of diffs — deterministic, not advisory |
| **Parallel sessions & subagents** | Multiple worktrees run at once; repeated jobs become scoped subagents (e.g. a verifier) |
| **Auto mode** | Once guardrails mature, Claude applies changes without per-edit prompts — review shifts to artifacts, not edits |

### Stage 4 — Test: every session checks its own work first

The configuration that steers the agent gets regression-tested like the code it writes.

**Feedback loop.** Claude is given a way to verify its own work — tests, build, or screenshot diff — and iterates until the check passes before a human sees it.
- For bug fixes: write the failing test first, confirm it fails for the right reason, then let Claude fix the code (never the test)
- For UI work: implement, screenshot, compare to mock, adjust — 2–3 rounds is normal

**Continuous evals in CI.** The AI-native equivalent of stage-gate QA. A suite of **20–50 real tasks** with expected outcomes runs nightly and on any change to `CLAUDE.md`, skills, or hooks.
- A configuration change that drops the pass rate is reviewed before it merges
- Every production incident becomes a permanent eval — a living regression suite

**Measure:** First-pass CI success rate for agent-written changes, and review time per PR — both should fall as tests catch what reviewers used to catch.

### Stage 5 — Deploy: review runs both ways; the agent stops at the gate

The agent does everything up to the production gate, and nothing past it.

| Play | Description |
|---|---|
| **AI in the PR review loop** | Claude reviews incoming PRs against `REVIEW.md` (bugs, security, compliance) and addresses comments on its own PRs. Findings never self-approve |
| **Hooks as approval gates** | A hook can pause an action until a named person approves — e.g. production deploys need a release authorisation |
| **CI/CD integration** | Claude runs non-interactively in the pipeline for judgement steps, sandboxed with scoped, short-lived credentials — no standing production access |

**Separation of duties is preserved: the agent that wrote the code has no way to approve it.**

### Stage 6 — Maintain: the loop closes itself

A trigger invokes Claude with no person in the invocation path. What it finds re-enters the loop as `intent.md`.

**Control-band response tiers** (from `bands.yaml`)

| Band | Response |
|---|---|
| 1σ | Log only |
| 2σ | Claude diagnoses (read-only) |
| 3σ | Claude proposes a PR or triggers an approved runbook |

**Recurring codebase scans.** Security scans run on a schedule, not just before release — each finding validated with a confidence rating, then routed through the normal PR review gate.

**Claude on call.** Claude joins incident channels as a first responder — diagnoses, verifies fixes, and writes the post-mortem to a version-controlled lessons file.

## Governance model — layered, not bolted on

| # | Layer | What it does |
|---|---|---|
| 01 | **Skills** | Advisory policy — makes Claude *likely* to comply while writing code |
| 02 | **Hooks** | Deterministic layer — block, ask, or allow actions. Makes violations close to impossible |
| 03 | **PR review + branch protection** | Separation of duties — the author of the code cannot approve it |
| 04 | **Sandboxing & permissions** | OS-level isolation, scoped credentials, no standing production access |
| 05 | **Continuous evals** | Regression-tests the agent's configuration itself, not just the code |
| 06 | **Audit trail (git history)** | Every artifact, prompt, and approval timestamped and traceable |

**The key distinction:** skills *advise*, hooks *enforce*. A control that must always hold belongs in a hook, not a skill.

Humans remain accountable for every decision requiring judgement — attention moves with the artifacts.

## Adoption guidance

The plays are modular. Start with any play that has no prerequisites. One sensible order:

1. **Capture intent** — `intent.md` home + template
2. **CLAUDE.md + skills** — institutional knowledge as files
3. **Plan mode + feedback loop** — approved plans; self-verifying sessions
4. **PR review + hooks** — automated review, approval gates
5. **CI/CD integration** — non-interactive pipeline steps
6. **Close the loop** — monitoring → `intent.md` → restart

**For every artifact, name one source of truth:**
- *Repo as source of truth:* markdown files are authoritative; legacy tools reference commits
- *Legacy system as source of truth:* Jira/ServiceNow holds the record; Claude reads/writes via connector
- *Linkage as minimum bar:* artifacts note the record ID; the record notes the commit SHA

## Measurement

Anthropic publishes **no outcome figures**. Instead it defines what to measure per play. Examples captured:
- Time from first conversation to committed `intent.md`
- First-pass CI success rate for agent-written changes
- Review time per PR
